# Published-package saved-review upgrade rehearsal

The owner requests the next high-value automatic goal and execution, without personal testing
or qualifying reviews. Live main/release checks are green. A generic release checker would not
prevent the earlier parent-shell publication incident and is not required upkeep. A concrete
bounded question remains: **can native records written by published v0.2.3 reopen and resave in
published v0.2.4 without lost facts or invented readiness?** Current legacy tests downgrade
current-writer payloads; the packaged browser journey uses only the current wheel.

## Chosen approach

Use the two immutable public ScopeProof wheels in separate external Python 3.12 environments.
Check asset hashes and installed identities, and compare their core Python files to their tags.
Generate one native v4 record using v0.2.3's own lifecycle/store APIs, with two criteria revisions,
historical and active synthetic runtime links, decisions and recorded final acceptance. Every
actor/scenario/limitation must identify constructed automation; use the packaged constructed demo,
not a genuine participant or target-repository execution. Save/reload under the old writer.

Preserve original bytes and backups. Copy into isolated v0.2.4 storage; load twice, export,
resave as v5 and reopen. Compare original facts including IDs, heads, source text/provenance,
timestamps, decisions, runtime IDs/links, criteria revisions and history. New source identity,
repository visibility, selection completeness and changed-file inventory must remain unknown
when absent; file-scope decisions must not be invented. Recorded acceptance must not conceal
unknown file scope or retain Ready. Same/changed-head detection uses offline constructed snapshots
and must not change saved identity/history or supply evidence.

Keep the unmodified old-writer-produced JSON plus generation recipe and strict Pydantic-validated
provenance. Add targeted offline tests for the native-producer boundary, which existing hand-built
legacy fixtures do not cover. Tests never install old packages or access the network. Record
version-bound results separately from frozen R-002. If a defect is found, use a failing regression
and the smallest safe fix; never weaken evidence rules or misdescribe the published reader as fixed
by a later development change. Stop with a precise blocker if that cannot be done safely.

## Constraints and finish line

No personal testing, qualifying reviews, target-code execution, release/tag/asset changes,
deployment, outreach, speculative features or Stage 3 advancement. Preserve all frozen research
and published bytes. Core remains independent of UI. No human/runtime/customer evidence credit.
Finish after the bounded rehearsal, concise evidence and durable regression, independent review,
required automated checks with 95% coverage, protected exact-head merge and resulting-main checks.
