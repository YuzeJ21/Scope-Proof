The confirmed blockers below have now been repaired on
`codex/v023-readiness-sync`. Positive final acceptance is rejected until every
current criterion has an eligible decision and the complete/passing review
prerequisites hold. Direct manual-verification events are rejected; matching
runtime evidence is independently required at bundle, state, persistence,

Stage 1.

## Confirmed release blockers at the audited public main

The following findings describe the pre-repair public `main` audit. The
integrity-repair continuation at the top of this document records their
verified resolution on `codex/v023-readiness-sync`; public `main` and the
published release remain unchanged.

### Core lifecycle can produce False Ready

`append_resolution()` accepts a final-acceptance event without enforcing
`can_record_final_acceptance()`. In a confirmed, completely ingested review
with passing observed CI and one unresolved `SHOULD_HAVE` criterion:

- `can_record_final_acceptance()` returned `False`;
- appending `final_acceptance=True` produced `Ready` with zero criterion
  resolutions; and
- `validated_review_state()` accepted the result as schema-valid and
  deterministically self-consistent.

The same core entry point also accepted a `MANUALLY_VERIFIED` decision without
the atomic `append_external_verification()` path. A subsequent final event
produced a schema-valid `Ready` review with zero `RuntimeEvidence` records.
The current workbench guards the intended UI path, but the exported core
lifecycle does not enforce the rule.

Release repair requires core-level rejection of ineligible final events and
unpaired manual-verification events, plus red-green regressions proving that
persisted and exported states cannot bypass either boundary.

### Candidate retrieval can lose exact-head anchoring

`fetch_candidate_files()` interpolates a validated-but-unencoded repository
path into a URL before adding `?ref=<head_sha>`. A candidate path of
`src/probe.py?mode=default` generated:

```text
/contents/src/probe.py?mode=default?ref=<head_sha>
```

The HTTP client parsed no `ref` parameter, but the returned `RetrievedFile`
still recorded the supplied head SHA. This can misstate immutable provenance
for explicitly requested unchanged candidates.

Release repair requires encoded path segments, a separately supplied `ref`
query parameter, strict SHA validation at the retrieval boundary, and
regressions for `?`, `#`, `%`, Unicode, and the actual transmitted `ref`.

### Follow-up hardening

These observations did not produce another demonstrated False Ready result,
but should be resolved or explicitly accepted before wider Action use:

- Action comment idempotency trusts any same-head marker without confirming
  comment author or app identity;
- most CI and Action installation paths resolve ranged dependencies rather
  than the checked-in lock; and
- Pages write and OIDC permissions are workflow-wide rather than scoped only
  to deployment.
