## Upgrading saved reviews

The current writer uses **saved-record format v5**. It accepts versions 1–5 and validates them
with Pydantic. Older records are reassessed under current policy; loading a pre-v5 record clears
unproven changed-file inventory and file-scope decisions rather than inferring that an uncited
file is accepted or out of scope. Gates may become more conservative. Source reconfirmation,
fresh analysis at the intended head, and explicit reviewer decisions may be required before a
review can be complete. Legacy core-source identity and selection counts remain unknown unless
they were actually recorded.

Keep a backup of the original local records and retain original exports before upgrading or
saving migrated reviews. Reopen and resave only the records you intend to migrate. Downgrade and
forward compatibility are not promised: v0.2.3 or another older executable may reject newer
records or diagnostic fields. An export is an evidence record, not a substitute for an editable
saved review or proof of correctness. See the [identity boundary](../development/engine-identity.md)
and [privacy/retention notes](../privacy-readiness.md).

## Supported environment and defect reporting

Python 3.11, 3.12 and 3.13 have package/CLI engineering coverage. Python 3.14 remains unverified.
Windows CLI/storage checks do not establish Windows desktop/workbench validation. Local storage
requires a filesystem supporting the documented atomic hard-link operation. Consult the
[environment guide](../development-environment.md) for exact limits. Packaged Chromium checks
are constructed automation, not independent use or WCAG conformance.

Use the [ordinary defect form](https://github.com/YuzeJ21/Scope-Proof/issues/new?template=defect.yml)
for the installed version, smallest reproduction, expected behavior and sanitized output.
Do not include private code, credentials or confidential data. Report vulnerabilities privately
using the instructions in [SECURITY.md](../../SECURITY.md).

## Verification and remaining publication gate

The preparation PR must pass independent agent review, exact-head hosted CI and CodeQL, including
the 95% unrounded coverage gate, locked environment, both deterministic benchmarks, Python/Windows
compatibility, installed-wheel checks and packaged-browser checks. Final candidate archives must
be built from the exact clean resulting main commit after that merge. A private candidate packet
records that SHA, hosted run identities, archive inventories/digests, commands/results, external
clean-install versions/import location/dependency check, both installed benchmarks and local
workbench health `ok`. It must distinguish completed checks from pending checks.

No release tag, GitHub Release, asset upload or deployment is authorized by preparation alone.
After separate publication authorization, the tag target, GitHub Release target and candidate
build SHA must match. Upload exactly the two verified archives and checksum manifest, then
download all public assets again, verify their hashes, clean-install the public wheel and repeat
installed benchmarks/health. Private candidate success is not public-download verification.
Publication and delivery do not advance Stage 3 or replace genuine independent-use evidence.
