## What the product does

ScopeProof helps a PM, QA practitioner, or engineer inspect whether a public
GitHub pull request contains credible candidate evidence for each explicitly
confirmed acceptance criterion at an exact PR head.

The workflow is:

1. load a public PR or the deliberately constructed demo;
2. normalize and explicitly confirm acceptance criteria;
3. deterministically retrieve candidate implementation and test evidence;
4. inspect cited lines and explanations for missing candidates;
5. record human decisions and optional external runtime verification;
6. fail closed unless all current evidence and decision gates are satisfied;
7. save, reopen, compare changed heads, and revisit affected decisions; and
8. export Markdown, JSON, CSV, or HTML evidence records.

It does not prove correctness, execute target code, replace QA, generate generic
code-review comments, scan security, or automatically fix a PR.

## Primary use cases

1. **Pre-merge acceptance-coverage review:** inspect which confirmed criteria
   have credible implementation or test candidates and which require more work.
2. **PM/QA-to-engineering handoff:** export a criterion-by-criterion record that
   keeps missing evidence and unresolved decisions visible.
3. **Changed-head re-review:** compare immutable prior and current candidates
   and revisit decisions affected by a new SHA.
4. **False Ready prevention:** refuse a Ready result when ingestion, checks,
   evidence, runtime requirements, or current human decisions are incomplete.
5. **Public engineering research:** run deterministic, hash-bound static cases
   without executing target repositories.

## Product maturity assessment

deterministic core. The clean implementation candidate closes the exact-head

regression coverage. It is ready for draft review, not a release decision:
public `main` still awaits the candidate merge and exact-resulting-main

an unsupervised beta, team rollout, commercial sale, accessibility-conformance
claim, or broad platform-support claim.

The strongest evidence is engineering reproducibility. The largest product gap
remains zero independent use.

## Prioritized post-release decision candidates

These are proposals, not authorized implementation. Each must preserve
confirmed criteria, typed evidence boundaries, immutable provenance,
deterministic fail-closed gates, Pydantic validation, and non-execution of
target repository code.

### Pilot-critical candidates

1. **Exact-SHA GitHub Check lifecycle:** design one low-noise check bound to the
   current PR head, invalidate stale prior conclusions on `synchronize`, and
   keep the current Action informational until independent use justifies
   promotion.
2. **Criteria-source snapshot and staleness detection:** record the source URL,
   source revision or hash, normalized confirmed text, confirmer, and
   confirmation time; require reconfirmation when the source changes.
3. **CLI lifecycle parity:** expose resolution, atomic external verification,
   final acceptance, and changed-head comparison through the core-backed CLI
   without weakening Streamlit or schema boundaries.
4. **Non-executing evidence adapters:** design validated import records for
   JUnit-style results, coverage summaries, contract reports, build/deployment
   records, and externally supplied runtime attestations. Imported data remains
   evidence with provenance, not proof of correctness.
5. **Authenticated reviewer identity:** current runtime records now retain
   review-scoped identity and attribution, but authentication, optional expiry,
   and externally signed attestations remain future decisions without accounts,
   silent overrides, or automatic approval.
6. **Real-browser regression coverage:** automate the packaged pointer path
   first, then add keyboard, responsive viewport, and zoom checks only where
   the execution environment provides trustworthy control.

### Demand-gated candidates

Jira or Linear intake, private repositories, collaboration, shared dashboards,
hosted processing, accounts, billing, paid APIs, and broader repository
support remain gated by genuine repeated use. R-003 remains design-only:
cohort generation and label confirmation retain separate owner gates, and
R-002 must not be retuned.
