# ScopeProof v0.2.3 status, gaps, and next stages

Date: 2026-07-27
Repository state: local internal candidate; not published  
Public install: v0.2.1  
Product-validation state: Stage 0 complete, Stage 1 waiting, Stages 2–4 gated

## What the product does

ScopeProof helps a PM, QA practitioner, or engineer inspect whether a public
GitHub pull request contains credible candidate evidence for each explicitly
confirmed acceptance criterion at an exact PR head.

The workflow is:

1. load a public PR or the deliberately constructed demo;
2. normalize and explicitly confirm acceptance criteria;
3. deterministically retrieve candidate implementation and test evidence;
4. inspect cited lines and explanations for missing candidates;
5. record human decisions and optional external runtime verification;
6. fail closed unless all current evidence and decision gates are satisfied;
7. save, reopen, compare changed heads, and revisit affected decisions; and
8. export Markdown, JSON, CSV, or HTML evidence records.

It does not prove correctness, execute target code, replace QA, generate generic
code-review comments, scan security, or automatically fix a PR.

## Current implemented feature ledger

| Capability | Current implementation | Evidence boundary |
| --- | --- | --- |
| Public PR ingestion | Anonymous public-GitHub loading with bounded files, immutable head SHA, CI observation, incomplete-ingestion handling, and optional temporary token | A fetched PR is not a validated use case |
| Criteria control | Parsing, normalization, add/split/edit/reorder/remove, and mandatory reviewer confirmation | Confirmation identifies scope; it does not prove satisfaction |
| Deterministic evidence retrieval | Exact identifiers, bounded lexical matching, file/evidence roles, immutable references, and conservative thresholds | Candidate lines are not correctness or runtime proof |
| Retrieval diagnostics | Per-criterion searched terms, identifiers, paths, evidence types, line/filter counts, accepted counts, and outcome | Diagnostics explain search and are not verdict evidence |
| Evidence matrix | Strong, Weak, None, and Incomplete presentation with priority, evidence level, and observed CI boundaries | Strength is candidate quality, not human acceptance |
| Reviewer workflow | Unresolved queue, next actions, append-only resolution history, and guarded external verification | Acceptance remains human-owned and head-specific |
| Fail-closed gate | Complete ingestion, current criteria, observed CI, evidence findings, runtime requirements, and current decisions | False Ready is treated as more harmful than False Blocked |
| Persistence and privacy | Pydantic-validated local JSON records, safe paths, reopen, single-record deletion, no persisted token | Local storage is not secure erasure or hosted collaboration |
| Re-review comparison | Unchanged, Relocated, Modified, Added, and Removed evidence; two-sided references; affected decisions requiring review | No acceptance is silently carried to a changed head |

## Primary use cases

1. **Pre-merge acceptance-coverage review:** inspect which confirmed criteria
   have credible implementation or test candidates and which require more work.
2. **PM/QA-to-engineering handoff:** export a criterion-by-criterion record that
   keeps missing evidence and unresolved decisions visible.
3. **Changed-head re-review:** compare immutable prior and current candidates
   and revisit decisions affected by a new SHA.
4. **False Ready prevention:** refuse a Ready result when ingestion, checks,
   evidence, runtime requirements, or current human decisions are incomplete.
5. **Public engineering research:** run deterministic, hash-bound static cases
   without executing target repositories.

## Product maturity assessment

ScopeProof is an internally reproducible alpha candidate with a substantial
deterministic core. It is mature enough for a supervised technical demo and a
genuine inbound public-alpha case. It is not yet evidence-backed for an
unsupervised beta, team rollout, commercial sale, accessibility-conformance
claim, or broad platform-support claim.

The strongest evidence is engineering reproducibility and conservative gate
behavior. The largest gap is still zero independent use.

## Stage roadmap

### Stage 0 — engineering foundation

Status: complete, with continuing maintenance.

Preserve the verified v0.2.3 internal candidate and its
retrieval, evidence-integrity, accessibility, packaging, and documentation
gates. Engineering work may improve trust, but does not advance Stage 1.

### Stage 1 — genuine public alpha

Status: `waiting_for_inbound_public_alpha_submission`.

Current counts:

- 0/5 qualifying reviews;
- 0/3 independent practitioners;
- 0/3 public repositories;
- 0/3 independently observed completed reviews under ten minutes;
- 0/2 reuse-intent signals.

Wait passively. Do not post, email, DM, comment, monitor repeatedly, or invent a
participant. R-001, R-002, R-003, constructed cases, and owner rehearsals remain
engineering evidence.

### Stage 2 — commercial discovery

Status: gated by Stage 1.

After Stage 1 only, test repeat use, decision impact, primary user, likely
buyer, replaced alternative, and voluntary willingness to discuss a price
hypothesis. Do not build billing, accounts, or paid APIs.

### Stage 3 — limited beta

Status: gated by Stages 1–2 and a separate owner decision.

Require unprompted repeat use, a genuine changed-head re-review, correct
understanding of evidence boundaries, independently understood exports, and
zero confirmed False Ready outcomes.

### Stage 4 — evidence-guided expansion

Status: gated by repeated genuine behavior and separate owner approval.

Possible later decisions include a local read-only private-repository adapter,
narrow collaboration handoff, shared policy packages, GitHub-native delivery,
requirements import, or a commercial license. None is currently authorized.
